# 문서 작성 원칙

> 이 원칙을 지키면 팀원과 AI가 문서만 읽고 같은 결과를 낼 수 있어요. PR에서 바뀐 문서는 Claude가 이 원칙으로 리뷰해요.

규칙을 기계적으로 적용하지 않아요. 독자가 문서를 이해하고 행동하는 데 방해가 되는지를 봐요.

AI가 읽는 리뷰 지침(`.github/docs-review.md`)은 팀 문서가 아니라서 영어로 쓰고, 이 원칙으로 리뷰하지 않아요.

## 모든 문서

### 한 문서에서는 한 주제만 다루기

독자가 한 문서에서 하나의 목적을 달성할 수 있게 해요. 다른 문서에 있는 내용은 복사하지 않고 링크해요. 같은 내용이 두 곳에 있으면 한쪽만 고쳐져 어긋나요.

| 문서 | 다루는 내용 |
|---|---|
| [PLANNING.md](PLANNING.md) | 과제 요구사항 |
| `docs/design/` | 구현 설계 |
| [CONTRIBUTING.md](../CONTRIBUTING.md) | 협업 규칙 |
| [GITHUB_GUIDE.md](GITHUB_GUIDE.md) | 협업 규칙을 따르는 단계별 명령어 |
| [AGENTS.md](../AGENTS.md) | AI가 지킬 규칙 |

**Incorrect:** 설계 문서에 브랜치 규칙을 다시 적어요.

**Correct:** 설계 문서에는 설계만 쓰고, 필요하면 CONTRIBUTING.md를 링크해요.

### 가치를 먼저 쓰기

문서 첫머리에서 독자가 무엇을 알게 되거나 할 수 있는지 알려 줘요.

**Incorrect:** "이 문서는 Diff를 설명해요."

**Correct:** "이 문서를 읽으면 Diff가 어떤 Patch를 만드는지 알고 바로 구현할 수 있어요."

### 해요체로 쓰기

저장소 문서는 해요체로 통일해요. 한 문서 안에서 "~한다", "~합니다"를 섞지 않아요.

### 용어와 코드 표기 통일하기

- VNode, Patch, Diff, Virtual DOM처럼 [vnode-spec.md](design/vnode-spec.md)와 [PLANNING.md](PLANNING.md)에서 쓰는 용어를 그대로 써요. 같은 대상을 다른 이름으로 부르지 않아요.
- 함수, 타입, 필드, 파일 경로, 명령어는 백틱으로 감싸요. (예: `useState`, `src/diff.ts`, `npm test`)

### 실제와 일치시키기

문서의 명령어, 파일 경로, 링크, 라벨 이름은 저장소에 실제로 있는 것과 같아야 해요. 코드나 설정을 바꾸면 그것을 설명하는 문서도 같은 PR에서 고쳐요.

### 규칙 문서끼리 충돌하지 않기

AGENTS.md, CONTRIBUTING.md, GITHUB_GUIDE.md가 같은 규칙을 다르게 말하지 않게 해요. 한 문서의 규칙을 바꾸면 나머지 문서에서 그 규칙을 언급하는 곳도 확인해요.

## 설계 문서 (`docs/design/`)

AI는 설계 문서대로 구현하고, 내용이 빠졌으면 구현을 멈춰요. 그래서 설계 문서는 읽는 사람이 추측하지 않고 구현할 수 있어야 해요.

### 요구사항 ID 연결하기

설계가 다루는 [PLANNING.md](PLANNING.md)의 요구사항 ID를 적어요. 리뷰어가 빠진 요구사항을 찾을 수 있어요.

**Correct:** "이 문서는 R1-2, R1-6을 다뤄요."

### 입력과 출력을 의미, 형식, 예시로 쓰기

함수의 매개변수와 반환값, 객체의 필드를 설명할 때는 의미, 허용 형식, 예시를 함께 써요. 이름과 타입만 있으면 구현자가 추측해야 해요.

**Incorrect:** `props: object`

**Correct:** `props: Record<string, string>`: 요소의 속성. 이벤트 핸들러는 포함하지 않아요. (예: `{ id: "app", class: "box" }`)

### 엣지 케이스와 실제 React와 다른 점 적기

빈 자식, 텍스트 노드, 같은 위치의 다른 태그처럼 경계에 있는 입력을 어떻게 처리하는지 적어요. 실제 React와 다르게 동작하는 부분은 따로 적어요. PR 설명과 발표에 그대로 쓰여요.

### 정하지 않은 내용 드러내기

아직 정하지 않은 내용은 비워 두지 않고 "미정"과 이유를 적어요. 빈칸은 이미 정한 것처럼 보이거나 AI가 임의로 채우게 만들어요.

### 공통 형식 변경 알리기

VNode 구조나 Patch 형식을 바꾸는 설계는 [vnode-spec.md](design/vnode-spec.md)를 같은 PR에서 고치고, 이슈에 `common-format` 라벨을 붙여요.
